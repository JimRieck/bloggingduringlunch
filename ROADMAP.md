### Onboarding
- [x] Signup → create blog/workspace flow — every author registration either creates a new org (becoming its `owner`) or joins one via invite code (becoming an `editor`); no more picking blindly from a public list of every org's name.
- [x] Invite team members; roles (owner / editor / reader) — each org gets an unguessable `invite_code` (`organizations.invite_code`), shown persistently to its owner in the site footer (not just once at signup — it survives reload/relogin). Anyone with the code becomes an `editor` and can actually create/edit posts, fixing an earlier gap where "joining" only granted read access. The code is validated (`lookup_invite_code` RPC) *before* the account is created, so a wrong code fails cleanly in the form instead of leaving a stranded account with no org. Still open: revoking/regenerating a code, and any UI for an owner to manage or remove members.
- [x] Reader vs. author account types — registration opens with "What type of user are you?" (Reader / Author), persisted as `profiles.user_type`. Readers skip the organization question entirely and are auto-joined (server-side, in `handle_new_user`) to a single shared "BDLReaders" organization on first use — first reader becomes its `owner`, everyone after joins as `member`. Verified: two readers land in the same org (no duplicates); two authors correctly end up as `owner` + `editor` of the same blog via invite code, and the second author's post-creation was verified to actually succeed under RLS. Actual per-blog "Subscribe" (follow a specific author's blog, not just being bucketed as a reader) and email notifications on new posts are still open — see Email below.
- [x] `/directory` page — lists every user across every org (avatar, email, reader/author type, organization), via a new `public.user_directory` view that intentionally bypasses the normal per-org RLS. Gated to logged-in users only; there's no real "platform admin" role yet, so any logged-in user (reader or author) can currently see everyone else's email/org — fine as an internal tool for now, but worth tightening to a real admin check before this is a public multi-tenant site. A small external-link icon next to the avatar (top-right, `App.jsx`) opens it in a new tab.

### Administration

Needs: a way to actually grant the role to a real account (a manual SQL update is fine to start), a way to mark an account disabled (e.g. Supabase Auth's `banned_until`, or a custom flag enforced via RLS + a login-time check) and have it actually block that user from writing/reading as themselves, and a real UI for the site admin to find a user and toggle it. Directly related to the "no real platform admin role yet" gap already flagged on `/directory` above — likely the same role should gate both.
- [ ] Org admin: invite people to the org — a dedicated UI component for an org's admin to invite others, instead of today's only mechanism (the raw `invite_code` shown as plain text in the site footer, see Onboarding above). "Org admin" here is the person who registered and created the org — today's `owner` role, assigned automatically to the first person to register a new org — not the separate, currently-unused `admin` value in the `org_role` enum (`owner`/`admin`/`editor`/`member`); no new role needed for this, just a real component for the `owner`. ### Content & media
- [x] Real posts CRUD — a rich-text editor (`PostForm.jsx`, built on Tiptap: bold/italic/headings/lists/blockquote/code blocks/links/images) at `/posts/new` and `/posts/edit?id=<uuid>` (same component, upsert on save so editing never creates a duplicate row and preserves the original slug + `published_at`). The landing page shows an author's own posts (`MyPosts.jsx`, draft and published, with status badges) instead of a static placeholder. Per post: Edit, View (opens the live post in a new tab), Copy link, Unpublish (any editor), and Delete (owner/admin only, matching the pre-existing RLS policy — confirmed RLS blocks it server-side even if the button were somehow clicked by a non-owner). Content is stored as real HTML and rendered via DOMPurify-sanitized `dangerouslySetInnerHTML` on the public tenant blog.
- [x] Blob storage for images/media — Supabase Storage `avatars` bucket (public read, write restricted to the owning user's folder) for profile images, clickable from the nav pane avatar at any time via `ProfileImageModal.jsx` (not just the one-time post-signup prompt). A second bucket, `post-images`, plus a `post_images` tracking table (a small per-org media library) backs post thumbnails and inline body images — `ImagePicker.jsx` (upload new or pick a past upload) is shared between both use cases.
- [ ] Import posts from WordPress — real content to bring over now that `bloggingduringlunch.com` is off WordPress.com (see Domain & DNS). WordPress's built-in exporter (Tools → Export) produces a WXR file (XML/RSS-based) with post content, dates, status, and images; needs a parser/import step mapping that into the `posts` table and pulling embedded images into the `post-images` bucket.
- [x] **Fixed the last leftover Day-1 placeholder**: the marketing page's "Prefer to just read? View the blog →" link (and, sharing the same code path, any logged-in *reader* with no author org) rendered a single hardcoded fake post from before multi-tenancy existed — never updated once real posts and multiple blogs shipped. Replaced with `RecentPosts.jsx`, a real platform-wide feed of the most recent published posts across every org (title, thumbnail, excerpt, attributed blog name, linking to the real `/blog/<org>/<post>` permalink), using the same safe two-step `organizations_public` join pattern as Search (not an embedded `organizations(...)` select, which crashes for a post outside the viewer's own org). Verified with two separate authors' posts showing correctly interleaved by date. Aside found while testing, not fixed here: the *first* reader ever to sign up becomes `owner` of the shared `BDLReaders` org (by original design, since something has to own it), which incidentally makes them satisfy the "has an author org" check and see their own (empty) post list instead of this feed — a real but narrow edge case, only affects that one account.
- [x] Real per-post permalinks — `/blog/<org-slug>/<post-slug>` now renders a single-post page (`TenantBlog.jsx`, extended with an optional `postSlug`), with a "← All posts" link back and a graceful "Post not found" state. List-page titles link to it. `getTenantUrl()` builds this path directly now instead of a `#slug` hash fragment — a hash never reaches the server at all, so nothing server-side (including the item below) could ever have told two posts apart under the old scheme.
- [x] Social link previews (Open Graph / Twitter Card images) — sharing a post link on LinkedIn/Slack/etc. was rendering as a bare generic title with no image, because those crawlers don't run JavaScript; they only ever saw the same static `index.html` shell regardless of URL, which has no per-post meta tags. Fixed with this project's first server-side code: a Vercel Serverless Function (`api/og.js`), routed in front of the SPA via a `vercel.json` rewrite specifically for `/blog/:org/:post` (matched *before* the catch-all SPA rewrite), that fetches the real post from Supabase (anon key, same public data RLS already allows) and injects `og:title`/`og:description`/`og:image`/`twitter:*` tags into `index.html`'s `<head>` before serving it — the same React app then boots normally underneath for real visitors. Deliberately defensive: any failure (bad slug, Supabase error, missing env var) just serves the plain unmodified `index.html` rather than breaking the page. **Not verified locally** — Vercel Functions and `vercel.json` rewrites don't run under `vite dev`, only on an actual Vercel deployment, so this could only be checked against the live production URL after pushing (e.g. `curl -A "LinkedInBot"`, or a platform's own link-debugger tool). No fallback image when a post has no `thumbnail_url` — the card is text-only in that case, since there's no suitable site-wide default OG image yet.

### Discovery
- [x] Site-wide search (`Search.jsx`, `/search`, a new nav-pane item) — finds authors (by display name, `user_type = 'author'` only), blogs (by org name), and post titles (published only), each via a 300ms-debounced `ilike` query against the existing `user_directory`/`organizations_public` views and the `posts` table — no new tables, views, or RLS needed, since those already scope correctly (RLS already keeps drafts out of a stranger's search results; explicitly filtered to `status = 'published'` anyway so an editor's own drafts don't show up as if they were public). Blog and post results deep-link via `getTenantUrl()`; author results are informational only (no per-author profile page exists yet, matching `/directory`'s existing lack of links). Currently gated behind login, like the rest of the nav pane.
- [ ] `ilike('%term%')` can't use a normal index (needs `pg_trgm` trigram indexes) — fine at today's scale, worth revisiting once there's real content volume.
- [ ] Open to logged-out visitors — right now search requires login for consistency with the rest of the nav pane, but discovery is arguably more useful *before* someone commits to registering.
- [ ] No per-author profile/permalink page to link search's author results to.
- [x] **Fixed a real crash**: the posts search embedded `organizations(name, slug)` directly off `posts`, but `organizations`' own RLS only allows a member to see their own org — so a search match belonging to a *different* org than the searcher's silently came back as `organizations: null`, and `post.organizations.slug` threw, blanking the whole page (no error boundary existed to catch it). Same class of bug `organizations_public` was built to avoid, on Day 1 — `TenantBlog.jsx` already used it correctly; `Search.jsx` didn't. Fixed by fetching posts and `organizations_public` separately and joining client-side. Reproduced with two real separate-org users before and after the fix.

### Testing
Before this: zero automated tests -- every verification in this project was done by hand (curl/psql, driving the browser). That's how bugs like the BDLReaders dropdown leak and the invite-code notice never being shown slipped through until manually re-tested.
- [x] Integration test suite (`src/web/tests/`, Vitest) — runs against a real local Supabase stack, not mocked. `npm test` in `src/web`. First suite (`tests/integration/signup.test.js`) covers all three signup paths: reader (auto-joins the shared BDLReaders org), author creating a new org (becomes `owner`, gets a working `invite_code`, free subscription auto-created), and author joining via invite code (becomes `editor` and -- the actual regression this exists to catch -- can really insert a post under RLS, not just get a DB row). Also covers an invalid invite code resolving to nothing. Uses a service-role client (`.env.test.local`, gitignored — see `.env.test.example`) only for teardown; every assertion goes through an anon-key client so it's genuinely exercising RLS the way a real user would. Unique emails per run + full cleanup in `afterAll`, verified repeatable back-to-back with no leftover data.
- [x] Bulk/concurrency test (`tests/integration/bulk-signup.test.js`) — 50 randomized signups (name, email, and a weighted-random split across reader / author-creating-an-org / author-joining-via-invite-code) run in concurrent batches of 10 against the real stack, using a deliberately small org-name pool so duplicate names are likely. **This caught a real bug on its first run**: `handle_new_user`'s "does this slug exist? no → insert it" check wasn't atomic, so two concurrent signups picking the same org name could both pass the check before either committed, and one would fail outright with a unique-constraint violation (surfacing to the user as signup itself failing). Confirmed via Postgres logs, then fixed in `20260901204542_fix_signup_race_conditions.sql` by reacting to the actual constraint violation (retry-on-conflict) instead of predicting it with a separate non-atomic check — the same race existed in the reader→BDLReaders path too, fixed with `ON CONFLICT DO NOTHING`. Re-ran 5x back-to-back post-fix with no failures. Also bumped the local auth rate limit (`supabase/config.toml`, 30→300 signups/5min) so the test itself doesn't trip it.

All of it has been verified manually each time (browser automation + direct DB checks — real verification, just not durable), but none of it persists as an automated test the way the Day 1 signup flows do.
