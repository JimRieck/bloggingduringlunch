### Administration
- [x] Site admin: disable accounts — a platform-wide `profiles.is_site_admin` flag (separate from the per-org `owner`/`admin`/`editor`/`member` roles), never self-assignable at signup, granted only via a manual SQL update in the Supabase SQL editor (`update public.profiles set is_site_admin = true where email = '...'`) — deliberately no self-service granting UI, matching the original plan for this. A `security definer` helper `is_site_admin()` (mirrors the existing `is_org_admin`/`is_org_member` shape) backs one new RLS policy letting admins `select` every row of `profiles`, and is generic groundwork for gating future admin-only features, not just this one. Disabling actually bans at the Supabase Auth level (`auth.admin.updateUserById(userId, { ban_duration })`, `'876000h'` to disable / `'none'` to re-enable) via a new Edge Function, `admin-set-account-status` — this project's second, built the same way as `invite-member`: verify the caller's JWT, then a service-role client checks `profiles.is_site_admin` before acting, and a target can't be the caller's own account (no accidental self-lockout). `profiles.disabled` mirrors the real ban state so the client has something to read at all (`auth.users.banned_until` isn't exposed through PostgREST), kept in sync by the same function call that sets the real ban. New `/admin` page (`AdminPanel.jsx`, linked from `NavPane.jsx` only when `isSiteAdmin`) lists every user with a Disable/Enable toggle. **Known, accepted limitation**: banning blocks new logins/token-refreshes immediately, but doesn't revoke an already-issued access token — a session open at the moment of disabling keeps working against the database for up to the 1-hour JWT expiry. Narrowed (not eliminated) client-side: `App.jsx`'s own profile fetch now includes `disabled`, and signs the user out immediately with a notice the next time it runs (e.g. on their next navigation), rather than relying purely on the token naturally expiring. Verified end-to-end locally: a non-admin gets "you don't have access" on `/admin` and a 403 calling the function directly; disabling a user blocks their next login attempt (confirmed `user_banned` from Supabase Auth) and signs out an already-open session; re-enabling restores login; self-disable is rejected. Not verified against production — granting the first real admin requires a manual SQL statement only the site's operator can run in the hosted project's SQL editor, the same category of manual step (and the same reason) as the invite feature's production email-click gap above.
- [x] Disabling an account also hides its posts publicly — caught immediately after shipping the bullet above: banning only blocks login, it does nothing to posts already published, so Search/`RecentPosts`/the tenant blog kept showing a disabled author's content. Fixed at the source (the `posts` select RLS policy) rather than patching each frontend query, so every public-facing consumer is covered at once; org members are unaffected and still see everything in their org (including a disabled member's posts) so they can unpublish/delete it themselves. **Shipped one real bug and caught it before pushing**: the first version wrote the disabled-check as a plain subquery against `profiles` inside the `posts` policy — but that subquery is itself subject to `profiles`' own RLS (self-only + `is_site_admin`), so for anon/other-org callers it always saw zero rows and silently never hid anything, regardless of the actual `disabled` value. Same root cause as the RLS-embed bugs hit earlier in Search/RecentPosts, just via a raw subquery instead of a PostgREST embed. Fixed with a `security definer` helper, `is_author_disabled()`, mirroring `is_org_member`'s existing shape. Verified end-to-end locally: a disabled author's published post disappears from an anonymous `posts` query and from the real `RecentPosts` page, and reappears immediately on re-enabling.
- [x] Org admin: invite people to the org — settled the open question from before building this: asked directly, "invite" means a real email sent to a specific address, not just a nicer view of the shared code. Built as `supabase/functions/invite-member` — this project's first Edge Function, chosen over extending the existing `api/og.js` Vercel-function pattern specifically because Edge Functions get `SUPABASE_SERVICE_ROLE_KEY` auto-injected at runtime (both locally under `supabase start` and on the hosted project) with nothing to configure, whereas a Vercel function would need that secret manually pasted into Vercel's dashboard. Detecting "this session came from an invite" needed a workaround: supabase-js has no distinct `INVITE` auth event (only `PASSWORD_RECOVERY` is special-cased; an invite link fires plain `SIGNED_IN`), so a `?invited=1` marker is appended to the invite's `redirectTo` and checked in `App.jsx`, reusing the same `passwordRecovery` state the forgot-password flow already drives. Verified end-to-end locally: invite email lands in Mailpit, accepting it creates the right `editor` membership (confirmed the new editor can really publish a post under RLS, not just get a DB row), re-inviting an already-registered email is rejected with a distinct, friendly message instead of a generic failure (auto-joining an existing account to a second org is out of scope — real multi-org membership semantics don't exist yet), and a non-owner calling the function directly gets a 403. Deployed via `npx supabase functions deploy invite-member`.

### Engagement & analytics
- [x] Post views, star ratings, and comments (`supabase/migrations/20260907154630_add_post_engagement.sql`, `StarRating.jsx`, `CommentSection.jsx`, wired into `TenantBlog.jsx`'s single-post view). Views are anonymous-friendly (no login, no `user_id` — just traffic against a published post); ratings and comments require login to write but are publicly readable, matching how every ordinary blog comment/rating system works. A viewer's own rating upserts on re-click rather than creating a duplicate (`unique(post_id, user_id)` + `onConflict: 'post_id,user_id'` — Supabase's `.upsert()` defaults conflict resolution to the primary key, not a named unique constraint, and silently throws a duplicate-key error without that option; caught in verification before it shipped).
